# 测试、验收与发布门禁

## 1. 本轮验证状态

已验证：本地版本识别、参考源快照、9 张截图阅读、星算助手只读 UI 与安装包结构、本机 app-server schema 离线导出。未验证：实际菜单注入、真实上游推理、Bridge 工作、Windows 安装/运行、性能与恢复实现。不得将下列测试计划写成已经通过的测试报告。

## 2. 共存模式（Bridge）的两层验收

**协议层（自动，可重复）**：`cargo test -p gptswitch-bridge` 起真的 bridge 与两根 mock app-server，断七件事：菜单合并与去重、按模型路由、只带 threadId 的续接跟着线程走、冷路径探测、子进程错误不被打扮成成功、没有托管 home 时退化成纯透传、宿主关闭 stdin 后自己退出（不留孤儿）。另外断言桥接脚本不会自我复制（`GPTSWITCH_BRIDGE_CODEX` 指回自己时停下）。

**真机层（人工，需要真 codex）**：

```bash
cargo build -p gptswitch-bridge                       # 先建 bridge（打包时由 beforeBuildCommand 自动做）
cargo run -q -p switch-core --example g0_apply_pipeline -- /tmp/g0-coexist
node scripts/g0/coexist-check.mjs /tmp/g0-coexist      # 起真 codex 两根，核对菜单与路由
```

`coexist-check.mjs` 断言：菜单里原生模型与我们的 slug 同时存在且无重复；用我们的 slug 起线程落在托管那根；只带 threadId 的续接仍落在同一根；以及「刚起的线程还没有 rollout」这类报错**来自 codex 本身**（同一句话直接问真 codex，答案必须一样）。它不去用户的真实 home 里写会话：原生路由只断言决策（日志里的 `why`），托管那侧的端到端在临时 home 里跑完整。

**界面层（人工，需要真宿主）**：在「Codex 配置」页开启共存 → 确认差异弹窗说的是「合并菜单」而不是「替换」→ 应用并重启 → 在 Codex 的模型选择器里看到原生模型在前、我们的模型在后，各选一次，确认前者走账号、后者走网关；再关掉共存并重启，确认菜单回到纯原生。

## 3. G0 实验步骤

使用测试 OS 账号或明确隔离且已验证生效的 `CODEX_HOME`，配合只记录合成请求的 mock 上游。准备 A/B 两供应商同名模型、一个 text-only、一个 image 声明模型，设置不同 context/effort。

1. 记录 Desktop/CLI 版本、签名与路径；导出对应 app-server schema，保存 hash。
2. 保存原始测试配置；创建合法目录和 provider；不写当前用户生产认证。
3. 启动 mock 网关，再以目标安装渠道真实启动 Desktop。
4. 截图原生模型选择器，确认两供应商名称可区分（显示名默认是 `供应商/模型名`，同名模型必须能一眼看出属于谁）；遍历 `model/list` 与 UI 对照。
5. 各发一个合成文本请求，捕获 alias、provider、上游 model、Key 标识与输出参数；必须四者一致。
6. 验证一次 function tool 调用和 tool result 续接，工具只执行无害 mock 函数。
7. 对 text-only 模型输入图片，确认明确拒绝；对 image 模型验证传输格式，不仅看菜单图标。
8. 改变 Key、context、effort、目录集合，逐项记录热更新/重载需求。
9. 在旧任务与新任务分别选模型，记录 provider 固定和上下文行为；不得假设全局 config 改动会迁移旧线程。
10. 模拟上游失败、网关退出与外部配置变化，恢复原生，确认原文件及非管理字段保持。
11. macOS 与 Windows 分别重复，Windows 需覆盖正常安装路径、空格/中文用户路径及实际安装渠道。

产物：脱敏输入/响应 fixture、UI 截图、版本矩阵、失败说明、目录样本、恢复 hash、明确的路线决定。

## 5. 自动化测试层次

### 领域与配置

Token 边界、推理集合、URL、精确模型 ID、null/unknown、能力交集、路由身份做单元测试。TOML golden corpus 包含注释、CRLF、内联表、quoted key、Unicode、重复/损坏结构、项目/profile 层。三方还原须覆盖字段原本不存在、当前值已被外部更改、其他工具使用同 provider ID。

### 故障注入

在 journal 各阶段杀掉测试进程；磁盘满、只读目录、Keychain 失败、文件占用、DB commit 失败、目录 hash 不匹配分别注入。验证重启恢复和 CAS。多进程同时申请同实例操作必须串行/冲突，不能后写覆盖前写。

### 协议一致性

每个适配器包含请求、缓冲响应、SSE、usage、错误、unsupported fixture。覆盖 UTF-8 被拆、单次 chunk 多事件、多行 data、空注释、工具参数逐字、多个并行 tool、工具 output 错序、无结束事件、超时、取消、上游断流和背压。

特别检查：流一旦提交不得跨 Key 重试；端点 429 不等于 API Key 永久失效；previous_response_id 不跨供应商；未知模型不能按名称推测到官方路径；自定义工具格式不能伪装支持。

### UI

组件测试覆盖字段错误、草稿保留、SecretField 清空、Select 未知值、禁用说明、Dialog 焦点、长名称、表格分页和应用阶段。WebView 与系统凭据测试不能由浏览器测试代替。macOS 与 Windows 的正式包要分别做真实窗口流程。

参考 DSH 的桌面边界，补充窗口重开/renderer 故障后的状态同步、托盘唤回、最小化/全屏恢复、多显示器窗口位置、重复释放不残留监听器。窗口重建期间网关继续服务，不能重放 apply.execute；外部链接使用系统浏览器且不能把配置窗口导航到第三方网站。未来若切 Electron，另测主进程/core-host 独立退出与消息协议失败，不能沿用 Tauri 测试结果。

## 6. 安全与隐私验收

- 用合成 canary Key / prompt / 工具参数，检查 SQLite、日志、诊断包、renderer 存储和 crash 报告不含秘密。
- 验证错误体回显、Authorization 各大小写、URL query、Bearer、cookie 等脱敏；allowlist 外字段不导出。
- 非授权 loopback 请求、非法 Host/Origin、CORS 预检、跨 origin redirect、超大请求均有明确拒绝。
- renderer 不具备任意文件读写/命令执行；前端不能请求已存完整 Key。
- 安装/升级不触碰用户 Codex auth、历史、MCP 和权限设置。
- 导入包含恶意路径、可执行 command、未知 schema 时拒绝/预览，不自动执行。

## 7. 视觉与无障碍验收

截图矩阵：两个平台 × 1280×840 / 960×640 / 200% 缩放 × 深色（以及实际发布的浅色）。核对 tokens、标题层级、对齐、固定底栏不遮内容、长中文/英文不溢出。

自动计算实际颜色组合的 WCAG 对比度；普通文字至少 4.5:1，大文字 3:1，需要识别的控件边界/焦点 3:1。状态同时有图标/文案；读屏可读取标签、错误和步骤变化；键盘可完成首次接入、模型编辑和恢复。禁用控件的低对比豁免不能用来隐藏原因。

## 8. 性能与可靠性

性能报告记录设备/OS/包版本、冷/热启动、测量数量和 p50/p95；与直连同一 mock/真实端点的对照才能得出网关额外开销。仅平均值不够。目标值见 PRD。

常驻资源按全进程树统计，分别记录窗口显示、隐藏到托盘和持续流量；隐藏窗口不等于 renderer 已释放。若更换 Electron 或新增内嵌网页，先重新建立预算和代表性网页场景，不把现有内存目标当作已可达到的指标。

可靠性包含 8 小时空闲托盘、100 次合成请求、20 个并发流、睡眠唤醒 10 次、网络断开恢复、上游慢读和取消。目标是无泄漏、无重启风暴、无错路由；负载目标根据个人工具范围调整，不宣称企业级吞吐。

## 10. 发布门禁与回退

稳定版必须满足：核心用例通过、双平台真实供应商至少两家、同名模型路由正确、Key 安全存储、配置故障恢复、工具语义/流式取消、无阻断安全问题、签名与更新校验、许可证资料齐全。

发布产物：安装包、checksums、签名/公证记录、SBOM、版本说明、兼容矩阵、已知限制、恢复说明。发现错路由、秘密泄漏或配置破坏立即阻止升级并撤回版本；提供签名的上个稳定包和 DB 兼容恢复路线，不能让用户手删配置自救。

## 两层端到端验证：谁能进 CI，谁只能人工

`scripts/g0/` 下的三个探针都要一个**真实的 Codex 可执行文件**
（`/Applications/ChatGPT.app/Contents/Resources/codex`，可用 `GPTSWITCH_CODEX_BINARY` 覆盖）。
GitHub runner 上没有它，也装不上（它是 ChatGPT 桌面端的一部分）。所以端到端验证分两层：

| 层 | 跑什么 | 在哪跑 | 拦得住什么 |
| --- | --- | --- | --- |
| 自动 | `cargo run -p switch-core --example g0_apply_pipeline`（CI 的 `pipeline` job） | 每次提交 | 计划 → CAS → 原子写入这条链路上的回归：产出物缺失、配置里没写目录、事务没停在 `awaitingReload` |
| 自动 | `node --check` + 依赖自检（CI 的 `probes` job） | 每次提交 | 探针脚本自己烂掉（语法错、引用了已删除的模块） |
| **人工** | `node scripts/g0/probe-catalog.mjs`、`probe-apply-pipeline.mjs`、`probe-full-loop.mjs` | 发布前，本机 | 宿主是否真的接受自建目录、helper 是否真的被调用、真实 SSE 是否按 Responses 契约还原 |

**发布前必须人工跑一遍第三层**，并把输出贴进对应版本的发布说明或 `docs/appendix/evidence-manifest.json`。
这一层没有 CI 兜底是环境限制，不是「暂时没做」——写在这里就是为了让它不会被忘掉。
