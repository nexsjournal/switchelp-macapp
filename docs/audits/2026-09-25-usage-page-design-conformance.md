# 用量页设计规范符合性审计 + 真实数据核对

日期：2026-09-25 · 范围：新增的**用量页**（扩展组第 4 个入口）在浅深两套主题、1440×900 与最小窗口 960×640 下的版面与语义，外加核心解析算法在本机真实会话记录上的核对。

方法：Playwright 驱动真机浏览器渲染 `http://localhost:5173/visual.html?view=usage`，页面内读 computed style、按 alpha 合成后算对比度、量 bounding box；脚本为仓库内的 `scripts/in-page-audit.js`。
颜色一律用 `?theme=` **冷启动**后再量（热切主题会读到插值色，见 [审计方法](../development/04-design-conformance.md) 第 2 步）。凡未实测的一律进「未验证项」。基线：工作区当前分支，dev server 复用已在 5173 的实例（strictPort）。

规格：[用量页](../design/07-usage-page.md) · 背景：[AITracker 调研](../research/06-aitracker-research.md)

## 0. 结论摘要

**用量页在两套主题、两种窗口尺寸下：重叠 0、溢出 0、紧贴 0、裁切 0、对比度不合格 0、点击目标不合格 0、每页恰好一个 `<h1>`、无正 tabindex、无横向滚动、表头全部带 `scope="col"`、无缺无障碍名的图标按钮。**

本轮量出并修掉 1 处真实版面缺陷，另有 2 处是门禁与实现核对阶段抓出来并修掉的**实现/文档错误**（不是版面问题，但都源自「把没量过的东西当成事实」，记在这里）：

| # | 现象 | 实测数字 | 处出处 | 状态 |
| --- | --- | --- | --- | --- |
| 1 | 窄窗口降到两列时，两排指标卡高度不一致 | 修前 `[88, 88, 110, 110]`；修后 `[110, 110, 110, 110]` | 第一排无说明文字、第二排多一行「含在输入内」 | 已修（`.metrics` 加 `grid-auto-rows: 1fr`） |
| 2 | 图表上方的峰值是个裸数字，标签没用上 | `usage.trendPeak` 键存在但零引用 | `src/i18n.test.ts` 的「字典里没有没人用的键」 | 已修（峰值文案改为由页面注入 `peakLabel`，图表不碰 i18n） |
| 3 | 文档/契约声称 `total == input + output` 恒成立 | 全量核对后**不成立**：32366 个事件里 2878 个（约 9%）两者差 ±1~7 | 只抽查前 80 个文件得到的结论，全量后被推翻 | 已修（契约注释、设计文档、Rust 测试同步改正） |
| 4 | 表格数值列的表头与数字对不上（用户截图） | 表头左对齐、单元格右对齐，同一列两者右边缘相差最大 **156.02px**；修后 **0** | 表头没跟着数值列改对齐 | 已修（数值列 `th` 加右对齐类） |
| 5 | 选中卡片里的供应商图标方块消失（用户截图） | 图标底与选中卡片底是**同一个 token**，对比比值 **1.00**（完全同色）；修后深色 **1.19** / 浅色 **1.20** | `.monogram` 与 `.providerItem.selected` 都用 `--bg-selected` | 已修（选中态图标底改 `--bg-elevated`） |

第 3 条是本轮最值得记的一条：**抽样得出的「无例外」不是结论。** 相关三处文字已统一改成「不可互相推算」，界面也因此不做任何加总暗示。

## 1. 逐项实测

### 1.1 几何（重叠 / 溢出 / 紧贴 / 裁切）

| 表面 | 主题 | 窗口 | overlap | overflow | touching | clipped |
| --- | --- | --- | --- | --- | --- | --- |
| 用量页 | 浅（`?theme=light` 冷启动） | 1440×900 | 0 | 0 | 0 | 0 |
| 用量页 | 深（`?theme=dark` 冷启动） | 1440×900 | 0 | 0 | 0 | 0 |
| 用量页 | 深（冷启动） | 960×640 | 0 | 0 | 0 | 0 |

冷启动已确认生效：`getComputedStyle(document.body).backgroundColor` 浅色为 `rgb(246, 246, 247)`、深色为 `rgb(8, 9, 12)`，不是过渡中的插值。

### 1.2 对比度与点击目标

| 主题 | 窗口 | 对比度不合格 | 详情 | 小于 32×32 的点击目标 |
| --- | --- | --- | --- | --- |
| 浅 | 1440×900 | **0** | `contrast: []` | 0 |
| 深 | 1440×900 | **0** | `contrast: []` | 0 |

判定线：正文 4.5:1，≥24px 或 ≥18.66px 且粗体 3:1。本页没有新增低于线的文本，也没有低于 32×32 的点击目标（`targetCount: 0`）。

**已登记的例外不受本页影响**：表单控件静息态描边（`--border-field`）低于 3:1 是 2026-09-21 的产品决定，本页没有表单控件。

### 1.3 字号分布（实测 `fontsUsed`）

两套主题一致：`12px ×25`、`13px ×62`、`14px ×30`、`16px ×4`、`24px ×4`、`28px ×1`。

- 12 是 `--font-size-caption`（表头、说明、轴标签），14 是 `--font-size-label`（正文、表格单元），16 是卡片标题，24 是 `--font-size-metric`（指标数字），28 是壳层 `h1`。
- **13 来自全局控件规则**（`button` / `input` 的 `--font-size-control`），属于**既有基线偏差**（规范写 14，`global.css` 给 13），本页的「重新扫描」按钮与三个页签继承的是同一套。这不是本页引入的问题，见 [04 审计方法](../development/04-design-conformance.md) 的「已知基线」。

| 侧栏宽度 | 184px（符合规范收窄值） |
| 内容卡宽 | 718px |

### 1.5 宽窗口（1440×900）

| 项 | 实测 |
| --- | --- |
| 指标卡列数 | 4（`275.5px ×4`） |
| 四张卡尺寸 | 276×110 各四张，**等宽等高**（含带说明文字的那张） |

指标卡在两种断点下都等宽等高——这正是「网格卡片要两层才等宽等高」那条规范的验收点（外层 `li` flex、内层 `flex: 1`）。

### 1.6 键盘与语义

| 检查 | 实测 |
| --- | --- |
| 正 tabindex | 0 |
| 负 tabindex | 0（`anyNegativeTabindex: []`） |
| `<h1>` 数量 | 1（「用量」） |
| 表格 `columnheader` 缺 `scope` | 0 |
| 缺无障碍名的图标按钮 | 0 |
| 页签语义 | `role="tab"` ×3，`aria-selected` 随点击变化（点「近 7 天」后该页签 `selected="true"`） |
| 本页可聚焦控件 | 5 个（刷新数据、三个页签、重新扫描），`tabIndex` 均为 0 |
| 焦点环 | 全局 `:focus-visible { outline: 2px solid var(--focus-ring); outline-offset: 2px }` 存在于样式表 |

**一处保留观察（P2，非本页引入）**：三个页签的 `tabIndex` 都是 0，即 Tab 会逐个穿过组内每个页签。ARIA APG 对 tablist 的建议是 roving tabindex（只留选中项可 Tab）。但这是共用组件 `SegmentedTabs` 的既有行为，工具管理 / 插件中心 / 内容中心三页同样如此；改它属共享组件改动，会同时影响四个页面，应单独立项并单独审计，**本页不动**。

## 2. 解析算法与真实数据核对

界面数字来自 `crates/switch-core/src/usage/mod.rs`。为避免「自己算自己验」，用一份**独立的 Python 实现**在同一批文件上算一遍，再与 Rust 输出逐项对比。

| 项 | 本机真实值（90 天口径） | Rust | 独立 Python |
| --- | --- | --- | --- |
| 扫描文件数 | 337（sessions 259 + archived 78） | 337 | 337 |
| 会话数 | 210 | 210 | 210 |
| input | 3,335,843,981 | ✔ 相同 | ✔ 相同 |
| cached | 3,124,826,125 | ✔ 相同 | ✔ 相同 |
| cache_write | 3,392,359 | ✔ 相同 | ✔ 相同 |
| output | 15,126,421 | ✔ 相同 | ✔ 相同 |
| reasoning | 3,713,314 | ✔ 相同 | ✔ 相同 |
| total | 3,350,970,424 | ✔ 相同 | ✔ 相同 |
| 按供应商（5 组） | OpenAI 2,029,016,983 / opencodex 695,472,077 / openai 335,138,211 / gptswitch 272,361,516 / custom 18,981,637 | ✔ 全组相同 | ✔ 全组相同 |
| 供应商合计 = 总合计 | 3,350,970,424 | ✔ 相等 | — |
| 不可读文件 | 0 | 0 | — |
| 计划窗口 | `plus`，已用 35，`window_minutes = 300`，`resets_at` 有值 | ✔ 相同 | — |

**算法依据（两条都是实测，不是推断）**：

1. **必须对 `total_token_usage` 做差分，不能累加 `last_token_usage`。** 本机 337 个文件里，「累加 last」在 110 个文件上大于最终累计值（例：最终 135386，累加 last 得 202636，虚高 50%）。而 `total_token_usage` 的六个字段在全部 337 个文件上**单调不减**（负差分 0 次），因此差分求和等于最终累计值，且可按时间戳分摊到天/模型/供应商。
2. **`total_tokens` 与 `input + output` 不恒等**：32366 个事件里 2878 个（约 9%）两者差 ±1~7，差值分布集中在 ±1~±7。所以四个指标卡只并列展示、写明「缓存读取含在输入内」，界面不出现任何加总暗示。

另有两处状态由实测确定：本机归档目录里存在 `.bak` 文件（文件名过滤只认 `rollout-*.jsonl`，不计入）；不存在 `.jsonl.zstd` 压缩会话（因此无需解压路径）。

`cargo test -p switch-core` 覆盖 10 条用例，其中专门锁住三件事：`last_token_usage` 重复计数时结果仍正确、范围外事件仍推进差分基准、三条分栏各自与合计自洽。**这是「按 last 累加」这个错误唯一会被自动挡住的地方**——它在本机 42% 的文件上会给出偏大的数字，靠人工看界面看不出来。

### 5.2 两个导航条目改名

| 键 | 修前 | 修后 |

实测侧栏渲染：`概览 / 网关 / 配置 / 内容中心 / 工具管理 / 插件中心 / 用量统计 / 连接诊断 / 日志`，分组标签仍是「扩展」「诊断」，页面 `h1` 同步为「用量统计」。

### 5.3 选中卡片里的供应商图标（问题 2）

`.monogram` 平时用 `--bg-selected` 压在 `--bg-surface` 上；而选中卡片本身的底**也是** `--bg-selected`——同一个 token，方块与卡片完全同色（比值 **1.00**）。选中态改 `--bg-elevated` 后的实测：

| 主题 | 卡片底 | 图标底 | 图标底 vs 卡片底 | 首字 vs 图标底 |
| --- | --- | --- | --- | --- |
| 深色（选中） | `#2b2e35` | `#1d2127` | **1.19** | **14.71** |
| 深色（未选中，对照） | `#15181d` | `#2b2e35` | 1.31 | 12.37 |
| 浅色（选中） | `#eaeaef` | `#ffffff` | **1.20** | **17.72** |
| 浅色（未选中，对照） | `#ffffff` | `#eaeaef` | 1.20 | 14.78 |

浅色下选中态与未选中态**完全一致（1.20 = 1.20）**；深色下 1.19 对 1.31，回到同一档的弱容器范围（这个仓库的卡片描边与分层本就是弱对比取向）。首字对比度 14.71 / 17.72，远高于 AA 的 4.5。

### 5.4 复测

| 表面 | 主题 | 窗口 | overlap | overflow | touching | clipped | contrast | hScroll |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 用量统计 | 深 / 浅 | 1440×900 | 0 | 0 | 0 | 0 | 0 | 无 |
| 供应商与模型 | 深 / 浅 | 1440×900 | 0 | 0 | 0 | 0 | 0 | 无 |
| 用量统计 | 深 | 960×640 | 0 | 0 | 0 | 0 | 0 | 无 |
| 供应商与模型 | 深 | 960×640 | 0 | **1**（见下） | 0 | 0 | 0 | 无 |

**「1 处 overflow」的判定与结论**：命中的是供应商详情面板里的**模型表**——它在 960 视口下面板只有 422px 宽，而 5 列 `nowrap` 的表需要 512px，容器是 `overflow-x: auto`（实测 `scrollWidth 526 > clientWidth 436`，可横滚）。也就是说这是**可滚动容器的正常行为**，内容并非被裁掉，页面级也没有横向滚动；审计脚本按「子元素宽于父容器」判定，不区分父容器是否可滚动。这处属**既有实现**（`src/features/models/ModelsPage.module.css` 的 `.tableWrap`，本轮未改；本轮对供应商页唯一的改动是图标底色，不影响几何）。

阈值：该溢出在 960px 为 83px、1000px 为 43px、**1100px 起消失**。

**没有去改审计脚本来把它排除**：这个脚本是仓库的量测工具，放宽判定会同时放过真正的裁切问题；应当单独决定是否给可滚动容器加例外，而不是为了这次好看就地松绑。

## 6. 未验证项

- **真机 Codex 路由下的数字**：本页读的是本机 Codex 会话记录，核对用的是真实文件，但**没有在 macOS 原生应用里**走一遍 `usage_report` 命令（本会话无法自动操作原生窗口）；浏览器走查走的是夹具数据，算法核对走的是直接调用核心函数。
- **Tab 顺序的人工走查**：只断言了可聚焦性与 `tabIndex` 取值，没有人工逐个 Tab 记录顺序；焦点环规则存在，但没有在真实键盘序列下量出外圈颜色。
- **200% 缩放**：未测。
- **共存模式下托管 profile 的用量**：`resolve_codex_home()` 按 `CODEX_HOME` → `~/.codex` 解析。共存模式的托管 home 在应用数据目录下，若本进程 `CODEX_HOME` 没指过去，**那部分用量不会被统计**。界面上的「扫描范围」一行会如实显示实际扫的目录，所以这种情况可见；但「切到共存模式后数字变小」这一现象未在真机复现过。
- **多语言下的排版**：只在中文下量了几何与对比度；英文文案更长，指标卡与表格的换行未逐条实测。
- **冷启动 `?theme=` 之外的主题路径**：设置页会覆盖主题偏好，本页不受影响；未验证「系统主题跟随」路径下的首帧颜色。
