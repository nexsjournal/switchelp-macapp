## 0. 方法与证据等级（先说清哪些是"看到的"，哪些是"推出来的"）

| 等级 | 含义 | 本次用到 |
| --- | --- | --- |
| **A 实测** | 浏览器里点击/读渲染结果 | **未执行**——本审计运行在无浏览器能力的子代理里（`Browser is not available in subagent`），dev server 只监听 IPv6 回环 `[::1]:5173`。见下"限制"。 |
| **B 代码事实** | 逐行读 `src/**` 的真实渲染逻辑与状态机，可定位到文件:行 | 全部主流程结论的主要依据 |
| **C 文档/前序审计** | PRD、设计文档、前两轮审计的实测记录 | 交叉核对 |
| **D 夹具** | `src/dev/visual-fixture.tsx` 的合成实现 | **仅用于确认控件文字与版面，不作为产品行为证据** |
| **E 未验证** | 真机行为、用户测试 | 明确列出，不写推断 |

**限制与替换方案**：原计划用 `browser-use:control-browser` 在 `http://localhost:5173/visual.html` 上亲手点一遍。该能力在本子代理内不可用，且 dev server 只绑 `[::1]`、本机 `http_proxy=127.0.0.1:7897` 会把 `localhost:5173` 变成 502，无法用 curl 补齐。因此**主流程改为按"真实渲染逻辑逐行推演点击序列"**（B 级），并以下述方式降低误判：

- 每一步都标出承载它的控件（文件:行）与它依赖的核心状态；
- 凡遇夹具的空实现（`saveProvider`/`saveModel` 不回写列表、`discoverModels` 返回写死数据、直连视图的关闭 = 跳转 `?view=providers`）一律标注 **[夹具]**，并按 `App.tsx` 的真实组合重新推演；
- 点击数是按"真实渲染逻辑"数出来的（B 级），不是像素级点击记录的替代物——真机点击数可能因骨架屏/自动选中差 1。

## 1. 产品定位再确认

**PRD 写的定位**：面向"已经使用 Codex Desktop、拥有自定义 API 服务商或中转 API Key 的个人开发者"，提供本地、可解释、可恢复的配置管理；核心是"用户知道自己选了谁、下一次请求去哪里、哪些能力真能用、失败怎么恢复"（`docs/01-product-requirements.md:5-11`）。

**代码实际交付的定位**：一个"Codex 配置的**事务管理器**"——它的信息架构、术语和状态机都是围绕"配置一致性"设计的，而不是围绕"让 Codex 用上我的中转"。

这个错位是本报告的主线。证据：

1. 六个侧栏页里，**四个**（Codex 配置、连接诊断、日志、设置）服务的是"可解释/可恢复"，只有**一个**（供应商与模型）服务"接进来"，而"接进来"才是用户来这里的唯一动机。
2. 首页（概览）的四个卡是：当前配置 / 连接状态 / 供应商 / 待应用模型。**没有一张卡回答"我装这个工具的收益是什么"**。
3. 侧栏副标题是"Codex 配置管理"（`src/locales/zh-CN.ts:75`），页头说明是"管理供应商与模型，让每一次切换都有清楚的状态"（`:587`）——两句话都在讲"管理/状态"，**没有一句出现"在 Codex 模型选择器里用上你自己的 API"**。

**结论**：定位在文档里成立，在界面上**不成立**。产品实际上把自己介绍成"配置治理台"，而它真正的卖点是"让第三方模型出现在 Codex 自己的模型菜单里"（README 第一句写对了，界面没抄过去）。这对目标用户是致命的：这群人的默认假设是"这不就是让我改 config.toml 吗"，界面必须在前 5 秒反驳这个假设。

## 3. 七个维度的判断

每维度：**结论 → 证据 → 对目标用户意味着什么**。

### 维度 1｜价值主张是否清晰：**不清晰（结论：需重写首屏文案）**

- **证据**：首次打开落在概览，若展开了向导，页头被隐藏（`App.tsx:209` `!showOnboarding &&`），用户看到的第一句是向导标题"首次接入"+ 副标题"建立正确的目标实例，并完成第一条可用链路"（`:104-105`）。**"目标实例""可用链路"是工程语言**，没有一个词提到"模型""菜单""Codex 里能用"。
- 若供应商列表已空但用户点过"稍后再说"，概览的空态是"添加第一个供应商"+ `overview.addFirstProviderBody`（`OverviewPage.tsx:75-77`），仍然只讲"加供应商"，不讲收益。
- 侧栏品牌副标题"Codex 配置管理"（`zh-CN.ts:75`）也不讲收益。
- **意味**：目标用户的第一反应会是"这不就是个 config.toml 图形界面吗，我用 codex-switcher / 手写就行"。README 第一句（"Make third-party providers show up in Codex's own model picker"）说对了，界面没抄过去。

### 维度 2｜流程是否简洁：**结构已经收敛，但三处"该替用户做的事"没做（结论：中上，可再省 3–4 步）**

- **能省的已基本省掉**：获取模型自动先落库（`ProviderForm.tsx:186`）——省一次保存；发现结果默认全选、一次写入（`DiscoverModelsDialog.tsx:33,60`）——省 N 次弹窗；保存后弹窗不关、可在原地继续加 Key / 加模型（`App.tsx:172-175`）——省往返；应用与重启合并（`PendingApplyBar.tsx:79-85`）——省一次"应用完再点重启"。
- **还没省的**：
  1. **预设**（卡点 B 的根）——把"API 格式 + Base URL 前缀"这种纯知识型输入变成一次点选。这是**流程上唯一能砍掉一个必填决策**的改动，PRD P0 已要求，竞品全都有。
  2. **模型长度核对**（卡点 C）——应该是"发现后默认标记为未核对，并进待办"，而不是让用户自己去编辑器逐个开。
  3. **"已加载"的人工确认**（卡点 E）——产品若无法观测，就该把它降级成一个可选的信息，而不是流程里的必经一步。
- **状态迷失**：memory 记的"保存了但没应用 / 应用了但没重启"两类迷失**已经解决**（PendingApplyBar + apply 内自动重启）。新出现的是"**应用结果是 Toast、5 秒后无处可查**"（卡点 D）。

### 维度 3｜信息架构：**对个人工具偏多，且有一组职责重叠（结论：6 页应收敛到 4 页）**

- 六个侧栏项：概览 / 供应商与模型 / Codex 配置 / 连接诊断 / 日志 / 设置（`App.tsx:25-29,194-197`）。
- **职责重叠最严重的一组是「概览」与「Codex 配置」**：概览的第一张卡就是"Codex 接入"（`OverviewPage.tsx:83` `t('codex.inspectTitle')`），展示已发布路由 + 目录版本，动作按钮是"查看模型 / **Codex 配置**"（`:101-102`）——也就是说概览的一半内容就是 Codex 配置页的摘要，两边都在讲"应用"。
- **低频页**：连接诊断、日志。二者都是"出问题了才来"的页，却与日常页平级占位。
- **PRD/设计文档的信息架构其实更干净**：`04-pages-and-flows.md:5-19` 写的是"供应商 → 供应商详情（连接/Key/模型）"、"模型 → 模型编辑"两级嵌套，**代码把它压平成了"供应商与模型"一页 + 六个平级导航**。这是实现阶段发生的架构漂移，结果是"模型"作为独立概念在导航里消失了（它现在只存在于供应商详情的嵌入表 `App.tsx:275` 和模型编辑器里）。

### 维度 4｜术语：**内部概念泄漏明显，四态模型过度设计（结论：需一份术语收口）**

| 界面用词 | 出处 | 判断 |
| --- | --- | --- |
| **目录 / 纳入目录 / 待应用目录 / 目录身份 / 目录版本** | `zh-CN.ts:239,258,555-559`、`error.duplicateAlias`"该目录身份重复" | **内部概念泄漏**。用户的心智模型是"模型出现在 Codex 菜单里"，不是"进入待应用目录" |
| **别名 / catalogAlias** | `ModelsPage.tsx:60`（搜索命中字段）、`error.unknownAlias`"该目录版本不包含此模型" | 内部标识进到了搜索与错误文案 |
| **实例** | `codex.instances`"Codex 实例"（`:112`） | 开发者能懂，但对"个人开发者"是多余抽象；"Codex 应用 / Codex 安装"更直白 |
| **重新加载 vs 重启** | 同一动作两种词：`action.applyAndReload`"应用并重新加载"（`:15`）、`codex.applyAndRestart`"应用并重启 Codex"（`:86`）、`codex.reloaded`"已重新加载"、`action.restartHost`"重启 Codex" | **同一个动作，界面上有 2 套动词**。这是最容易让用户"不知道点了会发生什么"的一类 |
| **档位 vs 推理等级** | 标题 `editor.levelsTitle`"推理等级（从低到高）"（`:268`）vs 正文全程"档位"（`:236,247,267,285,289`） | 同一概念两种词，同屏出现 |
| **能力 / 三态 / 未确认** | `editor.abilityTriState` | 概念本身是好的（未知 ≠ 不支持），但需要一句人话解释 |
| **已保存 / 已应用 / 已加载 / 已验证路由**（PRD §5） | 界面只实现前两个 + "等待重新加载"；`已验证路由` 无任何 UI；`已观测版本` 恒为"未观测" | **过度设计**。四态里有一态不可达。建议砍到三态（已保存 / 已应用 / 已重启），把"已验证路由"降级为一次真实请求后的可选诊断结论 |

**结论**：术语不是"有没有解释"的问题，是"要不要用户承担这套词"的问题。对一个本地个人工具，**目录 / 别名 / 实例 / 重新加载**这四个词应当从主路径文案里消失。

### 维度 5｜反馈设计：**单一 Toast 出口是进步，但对"应用"这类关键事务太轻（结论：方向对、层级错）**

- **做对的**：所有一次性反馈收敛到一个宿主（`Toast.tsx:12-23` 的判别规则：动作结果走 Toast、页面状态留内联条），且成功 5s / 信息 7s / **失败常驻**（`:31`）——失败不自动消失这条对个人工具是对的。
- **问题一（层级错）**：`应用 + 重启 Codex` 是**多阶段、不可逆、动别人文件**的事务，产出的结论有三种（重启成功 / 旧进程仍在 / 退出了没起来，`CodexConfigPage.tsx:112-121`），产品也确实把三种都说清了——**但它是用一条 Toast 说的**。用户一旦离开页面就没有回看入口；强制结束（`quitForced`）这种"可能丢了未保存对话"的严重信息也在浮条里。
- **问题二（无历史）**：Toast 队列最多 3 条、无历史（`Toast.tsx:29`）。日志页有记录但需要用户知道去日志页筛选（`LogsPage.tsx:132-160`），且日志是"诊断事件"，不是"我的操作历史"。
- **问题三（失败恢复是空白）**：失败时常驻的 Toast 说清原因，但恢复动作（`recovery`）只在 CodexConfigPage 里以"冲突→重新比较"一种形式露出（`CodexConfigPage.tsx:237-244`）；PendingApplyBar 里失败只 `setError` 进弹窗（`PendingApplyBar.tsx:87`），用户关掉弹窗后线索就没了。

### 维度 6｜"不做的功能"是否该做：**克制的方向对，但有三个"被方法论误杀"的能力（结论：部分优势、部分缺失，明确分档）**

PRD「当前不做」清单：官方账号轮换、OAuth 订阅导入、语音栏、GPT-Live、子智能体调度、会话迁移/删除、插件市场、远程控制、局域网网关、云同步、平台充值与价格商城（`01-product-requirements.md:52-54`）。

**判断为优势（明确支持继续不做）**：
- 语音栏、GPT-Live、子智能体调度、插件市场、会话迁移、远程控制、局域网网关、云同步、充值商城——这些是"综合工作台"的扩张，与"Codex 继续负责对话"的分工冲突，且每一样都要额外维护宿主兼容性。**对一个 MIT 本地工具，不做它们是正确的**：星算助手的这些功能正是它变重、可信度下降的原因。
- **"不展示没有可靠来源的余额 / 成功率 / Token 节省"**（`04-pages-and-flows.md:55`）——这条方法论是**产品优势**，应保留。

**判断为竞争力缺失（应当在下一个版本重新评估）**：
1. **官方账号 / OAuth 订阅导入**——目标用户（"已有自定义 Key 的个人开发者"）里有相当比例**同时**握着官方订阅和一家中转。星算助手与 codex-switcher 都能在两者间切。不做它，Switchelp 就只能是"第二工具"。这不是"克制"，是**主动放弃了最大的一块共存场景**。
2. **受约束的 Key 故障切换（PRD 已列 P1）**——中转 API 的典型故障就是限流/Key 失效。当前核心层把跨 Key 重试硬编码禁止（`04-pages-and-flows.md:89`），产品上也说"不做轮询/失败切换，做出来会是个假开关"。**理由是"核心做不到"而不是"用户不需要"**——这是把实现限制写成了产品结论。对中转用户，一家挂了就整个 Codex 挂掉，这是可感知的痛点。
3. **用量/健康最小视图**——被"不展示无来源数字"这条正确的方法论**一刀切**掉了。但**本工具自己就是网关**：`gateway.served`（已处理的推理请求数）已经被采集并显示在设置页（`SettingsPage.tsx:119`）。基于自家网关的真实请求数、近期失败率、各供应商的最近成功时间，是**有可靠来源**的，完全符合上述方法论。**这是当前投入产出比最高的留存功能，却被规则误杀了。**

### 维度 7｜差异化与留存/冷启动：**差异化真实但尚未被证明；留存钩子偏弱（结论：需要把"证明"当成 P0 产品任务）**

- **不可替代性**：与 CodexSplit（SwiftUI + Node sidecar，Windows 另起一套）、codex-switcher（切账号，不解决自定义 URL/模型能力/菜单）、星算助手（Electron 综合工作台 + 云端业务）相比，Switchelp 的真正差异是**"唯一一个把第三方模型写进 Codex 原生选择器、同时把 Key 留在系统凭据库、把写入做成可回滚事务"的跨平台 MIT 工具**（README:5-27）。
- **但这个差异目前是"未验证的"**：R03/R18（模型出现在原生选择器、选中后走对供应商与 Key）在两轮审计里都是"未验证"；README 自己也写"Desktop **GUI** model picker ... 未验证"（README:93）。**产品把全部价值押在一个还没被真机证明的宿主行为上。**
- **如果用户已经装了星算助手，为什么要换？** 目前的答案是"更轻、更可信、MIT"——这是**价值观理由，不是功能理由**。要变成功能理由，Switchelp 必须至少守住两条：①原生菜单里真的出现模型（要证明）；②不碰用户历史/不自动删东西（已做到，且是真差异）。
- **冷启动**：macOS 包**已签名但未公证**（README:44-47），首次打开要么右键→打开要么跑 `xattr`（README:36）。**对一个"顺手试试"的个人工具，这是最贵的一次摩擦**，而星算助手是双击 DMG。这一条与产品克制无关，纯执行，但它会直接决定冷启动转化。
- **留存**：第二次用的场景是"换 Key / 加一家供应商 / 某次请求失败来看原因"。托盘（PRD P0）提供了常驻理由，但没有"回来看看"的理由——**没有用量、没有余额、没有"上次请求走了谁"**。概览明确拒绝展示"最近请求使用"以外的实证内容（`OverviewPage.tsx:13-16`），于是第二次打开看到的和第一次几乎一样。

## 5. 最可能让产品失败的三个产品决策（不是 bug）

### 失败决策 1：把整个产品的价值押在一个"未验证的宿主行为"上，且没有 Plan B

**事实**：R03/R18（模型出现在 Codex 原生选择器、选中后按供应商+Key 路由）在 2026-09-19、09-20 两轮审计里都是"未验证"；README 自述"Desktop **GUI** model picker ... 未验证"，现有证据只在 app-server 层（README:88-94）。而**产品的一切都建立在这上面**：如果真机菜单里不出现第三方模型，供应商管理、Key 管理、能力编辑、事务应用全部归零，产品退化成"一个 config.toml 编辑器"。

更危险的是：**代码里已经有证据表明这个宿主行为会漂移**——`CodexConfigPage.tsx:154-158` 的注释写明"Codex 自己会写 `config.toml`（启动时补 `[projects.*]`）"，所以"生成计划 → 重启 → 提交"必然过期，只能自动重生成。宿主会改你的配置、宿主读配置的时机不由你控制——这不是一个稳定的集成面。

**为什么是产品决策而不是 bug**：产品选择了"不改宿主、不另造工作台"的路线（PRD 明确"不另造聊天工作台"），这条路线**只有当宿主配合时才成立**。而现在没有 Plan B：没有"托盘里切模型"的兜底，没有"Switchelp 自带一个最小模型列表"的兜底。建议：把"真机 GUI 菜单验证"提升为首发 P0 验收项（PRD §7 已写但要真的执行），并预研一个不依赖宿主菜单的兜底入口。

### 失败决策 2：用"配置治理"的完备性，换掉了"个人工具"的轻

**事实**：六个平级页面、四态配置模型（其中一态不可达）、"目录/别名/实例/待应用目录/目录身份"这套词、以及"已保存/已发布/已观测"三格版本面板——这些是**企业治理**的语汇和结构（Prodex 那一层的世界），不是"个人开发者顺手用一下"的东西。PRD 自己把目标用户定义为"已有自定义 API Key 的个人开发者"，并在非功能目标里写"新用户不编辑 TOML 即可完成"（`01-product-requirements.md:107`）——**当前的信息架构与术语密度与这个目标直接冲突**。

**为什么是产品决策**：这不是"文档写多了"，是每一轮迭代都在往"更完备"走。审计记录清楚地显示这个趋势：`04-pages-and-flows.md` 原本写的是清晰的"供应商/模型"两级结构，代码压平成六个平级导航；"已保存/已应用/已加载/已验证路由"四态被定义出来后，只有两态实现了，第三态被硬编码成"未观测"摆在界面上（`CodexConfigPage.tsx:276`）。**产品在持续为自己的内部状态机造 UI，而不是为用户的作业造 UI。**

### 失败决策 3：把"结果"做成一次性的浮条，把"证明"交给用户

**事实**：应用配置（写别人的文件 + 重启别人的应用）是产品的价值交付点，结果是一条 5 秒后消失的 Toast（卡点 D）；"Codex 是否真的加载了"要用户点"已重新加载"来宣布（卡点 E）；"模型是否真的路由对了"在产品里根本没有观测入口（已验证路由无 UI）。**产品在最需要确定性的三个点上，都选择了"轻"和"让用户自己判断"。**

**为什么是产品决策**：`Toast.tsx:12-23` 把"单一出口"写成了原则，这是对的；但把"应用"这种高价值、不可逆、跨进程的事务也算"一次性反馈"，就是把产品和用户之间最重要的一次交互降级成了通知。对一个"可解释、可恢复"为卖点的工具，**用户第一次应用配置后的不确定性，会直接决定他会不会用第二次**。建议把它改成页面级的结果面板（Q2-10），并给"真实请求已验证路由"一个最小入口（哪怕只是"复制一条验证命令"）。

## 6. 与竞品的差异化结论

| 竞品 | 它的核心 | Switchelp 相对它的位置 |
| --- | --- | --- |
| **CodexSplit**（原生 SwiftUI + Node sidecar） | 供应商分组、模型命名空间、原生菜单接入、黑灰 UI | **同一赛道、更轻的实现**：跨平台（Tauri + Rust 核心 vs macOS 原生壳 + 未公开的 Windows EXE）、MIT（CodexSplit 仓库未发现项目级 LICENSE）、不做"目录/宿主缓存/运行进程"多状态面对齐（`research/01-reference-projects.md:62`）。**如果 Switchelp 真机菜单验证通过，它就是"CodexSplit 的可审计、跨平台、开源版"** |
| **Codex Switcher**（Tauri + Rust） | 账号轮换、用量查询、OAuth 导入、托盘 | **互补而非竞争**：它解决"切账号"，不解决"自定义 URL/模型能力/菜单"。Switchelp 不做账号轮换是**正确的克制**；但这也意味着"想同时管官方订阅和中转"的用户需要装两个 |
| **星算助手**（Electron 综合工作台） | 模型中心、第三方服务商、工具配置、云业务、内嵌浏览器 | **定位相反**：它是"什么都做"的工作台，Switchelp 是"只做一件事"的管道。Switchelp 的优势是可信度（不上传遥测、不记请求正文、不导出密钥、Key 只进系统凭据库 —— `01-product-requirements.md:109`、README:77-84）；劣势是"没有回来的理由"（无用量、无余额、无平台目录） |
| **Prodex** | 企业级多供应商/多账户运行包装器 | 不同规模层，**只借鉴边界**（转换结果等级、续接绑定、输出开始后不换路），不构成直接竞争 |

**一句话差异化结论**：

> Switchelp 的不可替代性是 **"唯一一个把第三方模型接进 Codex 原生选择器、同时把凭据留在系统凭据库、把配置写入做成可回滚事务的跨平台 MIT 工具"**。
> 但这条差异里，**"接进原生选择器"还没被真机证明**（R03/R18 未验证），"凭据与事务"用户看不见（信任是隐性的，不产生切换动机）。
> 所以：**对已经装了星算助手的用户，Switchelp 目前提供的是"更可信、更轻"的价值观理由，而不是功能理由。**
> 要变成功能理由，只有两条路——**① 证明原生菜单真的生效；② 提供星算助手没有而中转用户真需要的两件事：多 Key 闭环管理与"我的请求走了谁"的用量视图。** 第二条是当前投入产出比最高的差异化动作，而它现在被"不展示无来源数字"这条（本身正确的）规则误杀了。

## 8. 未验证项（本机/本子代理验不了，不写推断）

1. **真机点击走查**：本审计运行在无浏览器能力的子代理里，未能亲手点完主流程。点击数为 B 级（按真实渲染逻辑推演），非像素级记录。
2. **真机 Codex 原生模型选择器**（R03/R18）：模型是否出现在菜单、选中后是否走对供应商与 Key。**连续三轮未验证，是产品最关键的未验证项。**
3. **`quitForced` 重启路径**：可能丢失未保存对话的兜底分支，需真机 Codex 才能触发。
4. **`CONFIG_CHANGED` 自动重新生成计划**：需 Codex 自己改 `config.toml` 才能触发。
5. **Windows 真机**：README 已自述"第三方模型在 Windows 上还不可用"（helper 的 `.cmd` 是未完成桩）——**这条自述本身就是一个产品范围问题**：PRD P0 要求"macOS 与 Windows 相同核心功能"，而 Windows 当前状态与 PRD 的 P0 定义冲突，建议产品侧明确"Windows 是否算首发平台"。
6. **可用性测试**：无任何真实用户测试记录。"5 秒内是否知道这是什么"、"首次接入是否卡在 API 格式"这类判断需要 3–5 个目标用户的出声思维测试，本报告只能给方向。
7. **200% 缩放 / 读屏**：设计审计 09-20 §8.1 已有 P1 结论（7/8 页横向滚动），本轮未复核。
8. **PDF 能力控件的灰态**：需实测确认。

---

**一句话总结**：Switchelp 的**机制**做得比它的**表达**好得多——它把"保存 / 测试 / 应用 / 重启"这条链的语义拆得很干净、还补上了缺失的"应用"入口；但界面把它自己介绍成了"Codex 配置治理台"，把最关键的一次交互（应用）做成了 5 秒的浮条，把最该由产品承担的判断（用什么协议、长度对不对）推给了用户。**下一个迭代最该做的不是加功能，而是：证明原生菜单真的生效（否则一切归零）、补回预设与搜索、把主路径文案从工程语言换成人话。**
