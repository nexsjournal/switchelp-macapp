## 0. 结论摘要

**达成。** 需求四条都有实测数字支撑，无数值未达标项；本轮另修掉一个被独立审查发现的真实缺陷
（很深/很暗的原色会被洗成中性灰，见 §3）。

先说要验的是什么。这个功能的难点不在「存一个色号」，而在**同一支色同时干两件相反的事**：
它既是底（主按钮、开关滑块、更新胶囊，上面压 `--accent-fg` 的字），又是字（链接、侧栏当前项，
压在自己的淡底上）。两个方向都要过 AA 4.5:1，可用亮度区间因此很窄——所以实现**不采用用户挑的
色号本身**，只取它的色相与相对饱和度，把明暗搬到 `tokens.css` 里那套**已实测**的青绿各档亮度上。

于是本次验收的核心命题只有一条：**换任何色相进来，对比度都不变。**

## 3. 本轮修掉的缺陷（独立审查发现）

**现象**：用户挑一支很深的色（如深玫红 `#3b0a12`），深色主题下强调色变成一块近乎中性的灰
`#c0bdbd`，彩度从 49 掉到 3。浅色主题下同样发灰（`#726667`）。
**为什么是问题**：界面文案承诺「只取你选的那个色相」，而变亮走的是**掺白**——掺白加得越多
彩度掉得越狠，这条路径下承诺是假的。取色器能选到任意色，所以它是可达路径。
**修法**：强调色本体那一档的「变亮」改成**抬明度、保持相对饱和度**（在 sRGB 里走固定饱和度的
色相线，二分落在目标亮度上）。淡底与描边仍走掺白——它们要的就是粉彩。
**修后实测**：`#3b0a12` → 深色 `#f1acb7`（彩度 69）、浅色 `#cb223e`（彩度 169）；对比度 9.15 / 4.85。
**副作用**：深色主题下非青绿预设也因此变得鲜艳（`#0891b2` → `#2bcef5`，此前是灰蓝 `#a3c3d2`），
与默认青绿本身的鲜艳度更一致；预设色相偏移从最大 11.7° 降到 **0.5°** 以内。
**与 tokens.css 的一致性未受影响**：默认青绿跑一遍推导，五档与 CSS 的最大通道差仍是
0 / 18 / 2 / 6 / 9（深色）与 5 / 5 / 0 / 1 / 6（浅色），与改动前逐位相同。

同轮修掉的三条较小问题：存储不可写时切主题会把已生效的颜色退回默认（现在记本进程最后一次
生效值）；存储里恰好是默认青绿那支色号时 9 枚色块会全不显示选中（现在读回时同样归一化）；
十六进制框的错误提示补 `role="alert"`（此前焦点留在框内时读屏不播报）。

## 5. 已知取舍（不是缺陷，改之前先读）

- **深色主题下所有色相落在同一亮度档**，因此蓝、青这类色相在深色主题下比青绿更「实心」，
  但亮度与对比度和默认青绿完全一致。若要让某个色相更暗或更亮，改的是 `accent.ts` 里那几张
  锚点表（`SHIPPED`），不是单个色号。
- **亮色主题的 `--accent-subtle` / `--accent-border` 与 `tokens.css` 原值有 1~6 个通道单位的差异**，
  深色 `--accent-strong` 差 18（原值人工加过彩度）。都是推导与手抄取值之间的正常误差。
- **用户若选绿色强调色，它与 `--status-success-dot` 会接近**。状态另有文字与图标，不靠颜色
  单独表达，所以不阻断；但如果以后要收紧，杠杆是给预设去掉绿，不是改状态色。
- **默认档（`'default'`）不写任何内联变量**：`tokens.css` 原值即默认。实测确认默认状态下根元素上
  0 条内联覆盖，选自定义色后 5 个变量（8 条声明）全在。
- 十六进制框**只在按回车且内容非法时提示**，失焦时静默还原：正在输的一半必然非法，实时报错会一直闪红。
