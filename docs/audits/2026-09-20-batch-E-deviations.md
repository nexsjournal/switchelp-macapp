# 批次 E 的两处「说清楚」而不是「补上」（2026-09-20）

批次 E 原本列了六项功能补齐。四项做完了，另两项**没有按原样实现**——这里的处理方式是
把它们从「看起来有」改成「明确没有」，并写明为什么。记在这里，免得下一轮有人照 PRD 的
旧文再实现一遍。

## 1. 供应商预设：删除死接口，不再假装提供

**原状**：`DesktopClient` 有一个 `listPresets()`，实现恒为 `async () => []`，而**没有任何界面调用它**。
`Provider` 上还有一个 `presetId` 字段，从来没有被写入过。

**为什么没有直接实现**：PRD 对预设的要求是「以填表辅助方式提供，**不能绑定推荐或充值**」。
要真的做，得先定一份「哪些供应商、哪几个 Base URL、协议是什么」的清单——那是一个产品内容决策
（选谁不选谁、地址写哪个、厂商改名了怎么办），不该由实现方凭空造一份塞进代码里。
本机可观察到的做法（星算助手、CodexSplit 的预设）都带着自己的商业立场，不构成可直接照搬的依据。

**本轮处理**：
- 删掉 `listPresets()`（接口 + transport + 夹具 + 测试桩）：一个永远返回空的接口看起来像功能存在。
- `presetId` 字段留在数据模型里（它已进库表结构），但代码里没有任何地方写入它——这是既有事实，未改动。

**需要用户决定**：要不要做预设。要做的话，最小形态是「用户自己保存的地址模板」（不预置任何厂商），
这样既解决「每次都要手打地址」又完全不涉及推荐立场；这与「预设」在 PRD 里的描述不同，属于范围变更。

## 2. 工具调用门禁：CC 适配明确标实验，而不是补一个门禁

**原状**：PRD 写「Responses 原生兼容路径；Chat Completions 适配**通过工具调用门禁后进入首发**，
未通过则明确标实验状态，不能冒充完整可用」。门禁本身（用真实上游跑一遍工具调用并记录结论）
从未实现，前端那个「实验」标签是一句静态文案，跟着协议名走，和实际发生过什么无关。

**为什么没有直接实现门禁**：门禁的产物是「某个供应商的某个模型 + 某个协议组合下，工具调用确实可用」
这样一条实测结论，它必须由**真实上游**产生。在没有可用测试凭据的情况下写出来的「门禁」，
只会是一条恒真的检查——比没有更坏。

**本轮处理**：走 PRD 给的另一半——**明确标实验状态**，而且标在**应用之前**：
`plan_apply` 只要发现本次发布有模型走 CC 适配，就往计划里加一条
`warning.chatAdapterExperimental`（说明工具调用未验证），它会显示在应用差异弹窗的警告区里。
文案在 `zh-CN.ts` / `en.ts` 的 `warning.chatAdapterExperimental`。

**需要用户决定**：要不要提供一份可用的测试凭据来跑真门禁。在此之前，CC 适配的状态就是
「文本可用、工具未验证」，这是当前代码与文档一致的口径。
