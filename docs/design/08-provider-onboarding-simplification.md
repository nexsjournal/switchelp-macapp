# 08 · 接入一家供应商：现状走查与简化方案

> 2026-09-30 · 应用户要求（「现在这个过程感觉有点太复杂了」）对**添加供应商 → 加模型 → 生效**整条链路做的走查与改版提案。
> 步骤数都在视觉夹具（`/visual.html`）里实际点过一遍数出来的，不是估的。

## 一、现状走查（以接入 DeepSeek 为例）

| 阶段 | 步骤 | 交互 | 卡点 |
| --- | --- | --- | --- |
| A 建供应商 | 1 | 点胶囊行「＋ 添加供应商」 | — |
| | 2 | 点预设「DeepSeek」，名称/地址/协议自动填好，焦点落在 Key | — |
| | 3 | 粘贴 API Key | — |
| | 4 | 点「保存」→ Toast「已保存」，弹窗关闭 | **落点缺失**：选中态不跳到新供应商，用户要自己在胶囊行里找 |
| B 加模型（推荐路） | 5 | 点新供应商胶囊 → 「编辑配置」 | **同一个弹窗开第二遍** |
| | 6 | 点「获取可用模型」 | 需要已落库的 Key（已自动处理，但入口藏在弹窗里） |
| | 7 | 勾选弹窗确认「添加 N 个模型」 | 上游不返回长度，全部按默认值写入 |
| | 8 | 关闭弹窗（或直接关掉去应用） | — |
| B' 加模型（手工路） | 5'–8' | 编辑配置 → 添加模型 → 填上游 ID/上下文/输出/协议 → 保存 | 字段多；协议、高级配置对首用是噪音 |
| C 生效 | 9 | 待应用条「应用并重启 Codex」 | — |
| | 10 | 差异确认弹窗 → 提交（自动重启 Codex） | — |

**合计约 10–11 次交互、两个界面往返、一次弹窗重开。** 三段里每段单独看都合理（这也是历次走查定下来的），但连起来有四个真实的断点：

1. **保存后的落点**（实测）：保存只给了 Toast，新供应商既不被选中、也没有任何下一步入口；想继续加模型必须重新找到它、再开一遍同一个弹窗。
2. **「获取可用模型」藏了一层**：预设厂商全都支持 `/models`，但发现动作要等保存之后再进弹窗才能点。
3. **预设不认识模型**：DeepSeek/Kimi/GLM/千问的旗舰模型 ID 公开且长期稳定，现在却要等一次发现请求（或手工填）才有模型。
4. **同一事实多处呈现**：模型列表在弹窗里一份、页面表格一份；测试连接入口三处（弹窗行、模型行、页面「测试全部」）。

## 二、目标与非目标

**目标**：从「有一家厂商的 API Key」到「模型出现在 Codex 菜单里」的交互次数 ≤ 8；每一步都有可见反馈；不破坏既有决定（保存即关闭、同一件事一个入口）。

**非目标（不做）**：不自动填 Key、不替用户应用（应用永远要显式确认）、不删除手工路径、不做账号体系、不自动下载任何东西。

## 三、方案

### 方案一（推荐先行）：保存后闭环 —— 把 B 段接在 A 段后面

改动集中在 ProviderForm 与 App 的保存回调，不新增界面：

1. **保存成功后选中态跟随**：新建的供应商立即成为胶囊行的选中项（详情卡同步切过去）。
2. **预设来源 + 已填 Key 的保存 = 自动发现**：保存成功后直接发起 `discoverModels`，把「选择要添加的模型」勾选弹窗接在保存动作后面（同一个连续流程，不用重开弹窗）。确认后模型入库，Toast 给出「已添加 N 个模型」。
3. **完成态指路**：全部确认完，Toast/待应用条已经承担「去应用」的指引（待应用条就在页头下方，不新增常驻 UI）。

效果：A+B 合并为 **5–7 次交互**（添加 → 预设 → Key → 保存 → 勾选确认 → [查看差异/应用]），不再重开弹窗。
代价：保存的语义从「存这条」变成「存这条并接着配」——需要**保留不勾选直接关闭的自由**（勾选弹窗的关闭按钮就是「先不加模型」），不改变「保存成功即关弹窗」的既有决定（弹窗本体仍然关闭，接上来的是发现弹窗）。

### 方案二（中改）：预设内置常用模型清单

在 `presets.ts` 里给每家预设加 `recommendedModels`（DeepSeek：`deepseek-chat` / `deepseek-reasoner`；Kimi：`kimi-k2-*`；GLM：`glm-4.6` / `glm-4.5-air`；千问：`qwen-plus` / `qwen3-coder-plus`；MiniMax：`MiniMax-M2`）：

- 选预设时把模型以「推荐 · 待确认」的形式预填进模型区（标注来源是内置清单、日期），保存时一次写入；
- 「获取可用模型」降级为**刷新清单**的手段（清单过期、换 Key、上游新增模型时才需要）；
- 离线也能完成接入——发现请求失败不再阻断主流程。

效果：方案一之上再省掉发现请求的等待与失败分支；**A+B 合计 ≤ 6 次交互**。
代价：内置清单会过期（每家 3–5 个模型，写清「截至 2026-09」），要在 UI 上如实标注并保留发现/手工两条更正路径。

### 方案三（减法，另行评估）：同一事实只呈现一次

- 弹窗里的模型列表与页面上的模型表格**二选一**：倾向保留页面表格（承载批量/排序/测试全部），弹窗里收成一行摘要（「N 个模型 · 获取/添加入口」），点「管理模型」关弹窗看表格；
- 测试入口收敛：弹窗「连接测试」行保留（它是接入时的唯一快速验证），模型行的单行测试与页面「测试全部」并存但在视觉上归入同一组。

### 被否掉的备选

- **分步向导卡**（选厂商 → 填 Key → 选模型，三张卡）：步骤固定、跳过性差，与「一个供应商一条线」的单弹窗版式冲突；自动接续（方案一）用更少的界面达到同样的引导效果。

## 四、分期与验收

| 期 | 内容 | 验收 |
| --- | --- | --- |
| 第 1 期 | 方案一全部 | 实测接入一家预设厂商（有 Key）≤ 7 次交互；保存后选中态跟随；自动发现失败时回落到现状路径且说明原因 |
| 第 2 期 | 方案二 | 离线状态下选预设 → 填 Key → 保存，模型清单即出现；内置清单标注「截至」日期；发现仍可刷新 |
| 第 3 期 | 方案三 | 模型列表只剩一处完整版；测试入口归组；走查确认没有丢失任何既有能力 |

每期都要过：vitest 全绿 + 版面审计（两主题）+ 真机用包内 codex 走一次 A/B（临时 CODEX_HOME）。
